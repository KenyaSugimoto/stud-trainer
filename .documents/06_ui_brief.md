## 1. プロダクト概要（3〜6行）

Stud Trainer は、Stud Hi / Razz / Stud8 などスタッド系ポーカーを CPU 相手に練習できる Web アプリです。
2〜7 人構成・任意の初期スタックで素早くゲームを立ち上げ、3rd〜7th までの進行・スタック推移・勝敗を一画面でプレイできることを目指します。
サーバーレスな SPA としてブラウザ内で完結し、オフラインに近い体験で「ルール理解」と「実戦感覚」の両方を高めることが目的です。

---

## 2. 主要ユースケース（最大5つ）

1. **UC-01: CPU 相手に 1 ハンド通してスタッドを練習する（最重要）**
   - 任意のプレイヤー数・ゲームタイプでゲームを開始し、3rd〜7th のアクションを入力しながら 1 ハンドを完走する。

2. **UC-02: 同一構成で複数ハンドを連続プレイする**
   - 一度設定したプレイヤー数・初期スタックを維持しつつ、Next Hand で連続して練習する。

---

## 3. ペルソナ（1〜2名）

### ペルソナ1：ミックスゲーム好きな中級プレイヤー（個人）

- 役割
  - オフライン / カジノ /ハウストーナメントでミックスゲームを打つプレイヤー
- 利用頻度
  - 週 3〜4 回、1 セッションあたり 20〜60 分程度
- ゴール
  - Stud Hi / Razz / Stud8 のルールと基本的な進行に慣れ、実戦前のウォームアップや新ルール習得に使いたい。

---

## 4. クリティカルユーザーフロー（3〜5本）

### FLOW-001 新規ゲーム開始〜1 ハンド目開始

- 目的
  - 希望するプレイヤー数・ゲームタイプ・スタックでゲームを素早く開始する。
- 開始条件
  - ユーザーが `/`（ゲーム設定画面）を開いている、またはゲーム画面から「新規ゲームに戻る」を選択した状態。
- 主要ステップ
  1. プレイヤー数セレクトで 2〜7 人から選択する。
  2. ゲームタイプ（Stud Hi / Razz / Stud8）を選択する。
  3. 初期スタック入力欄にチップ数（例: 20,000）を入力（デフォルト値あり）。
  4. 「ゲーム開始」ボタン（主 CTA）をタップ。
  5. `startGame` が呼ばれ、`initGameState` → アンティ徴収 → 3rd のカード配布 → bring-in 判定が実行される。
  6. 3rd Street・現在アクター・ポット・プレイヤー情報が表示される。
- 成功条件
  - GameScreen に遷移し、すべてのプレイヤーとカード・スタック・現在アクターが矛盾なく表示されている。
- 失敗/例外パターン
  - 入力値が不正（プレイヤー数範囲外、スタック未入力、0 以下）→ バリデーションエラー表示・主 CTA 無効。
  - 内部エラー（ほぼ想定外）→ 「ゲームをリセット」ボタンとリトライ導線を提示。

---

### FLOW-002 ハンド進行（3rd〜7th）でアクション入力

- 目的
  - 各ストリートで適切なアクションを選び、ゲームを進行させる。
- 開始条件
  - GameScreen 上で handFinished = false、現在アクターが存在する状態。
- 主要ステップ
  1. 画面中央〜上部で現在ストリート（3rd / 4th / ...）と現在アクターを確認する。
  2. 自分のプレイヤー行を確認し、スタック・ベット額・カード情報を把握する。
  3. 現在アクターのみにアクションボタン群（fold / call / bet / raise / complete / bring-in / check など許可済みのみ）を表示。
  4. ユーザーがボタンをタップ → `applyAction` が呼ばれ、スタック・ポット・アクションログ・アクターが更新される。
  5. `shouldEndStreet` 判定によりストリート終了なら `goToNextStreet` が呼ばれ、次ストリートのカード配布とアクター決定が行われる。
- 成功条件
  - 常に「誰のアクションか」と「可能なアクション」が一意に見える状態で、矛盾なくストリートが進行する。
- 失敗/例外パターン
  - 許可されないアクション（例: 既にオールインしたプレイヤーのベット）→ UI 上でボタン非表示とし、原則発生させない。
  - 不整合（バグ）によりアクター不在 / 生存プレイヤー 0 → 全体リセット推奨ダイアログを表示。

---

### FLOW-003 ショーダウン・勝敗確認〜次ハンド開始

- 目的
  - ハンドの結果を確認し、スタックを更新したうえで次ハンドへスムーズに移行する。
- 開始条件
  - `street === "showdown"` になり、勝者と分配結果が計算された状態。
- 主要ステップ
  1. 画面上部に「Showdown」ラベルを表示。
  2. 各プレイヤーの最終ハンド（Stud Hi 役評価結果）を表示し、勝者をハイライト。
  3. ポット総額と分配結果（Split Pot の場合は複数名）を表示。
  4. handFinished = true に応じて「Next Hand」ボタンを表示（主 CTA）。
  5. 「Next Hand」押下で `startNextHand` が呼ばれ、スタックを維持したまま新しい 3rd Street が初期化される。
- 成功条件
  - 誰がどれだけ獲得したかが一目で分かり、ワンタップで次のハンドへ進める。
- 失敗/例外パターン
  - ショーダウン前に全員フォールド→ 自動的に残り 1 人を勝者として表示。
  - 分配計算で不整合 → 「計算エラー」メッセージとともにリセット導線を表示（頻度は極小想定）。

## 6. 画面ごとの状態設計ガイド

### 6.1 共通状態モデル

- **loading**
  - 表示要素: スピナーまたはスケルトン UI、現在のコンテキスト文言（例: 「ハンドを初期化中…」）。
  - ユーザーの次アクション: 待機のみ。キャンセルが必要なケースは基本なし。

- **empty**
  - 表示要素: 該当データが存在しない旨のメッセージ＋次の行動を促すボタン。
  - ユーザーの次アクション: 新規作成（例: ゲーム開始 / ログ取得のためゲームをプレイ）。

- **error**
  - 表示要素: シンプルなエラーメッセージ（技術詳細は隠す）＋「再読み込み」「リセット」などのボタン。
  - ユーザーの次アクション: 再試行、またはゲーム全体のリセット。

- **success**
  - 表示要素: 通常画面＋必要に応じてトーストやラベルで完了を示す。（例: 「Next Hand を開始しました」）。
  - ユーザーの次アクション: 続行（次のハンド、次のアクション）。

- **permission（必要なら）**
  - 現状はログインや権限制御がないため未使用。将来、ユーザー別ログを扱う場合は「ログインが必要です」状態を追加。

### 6.2 画面別の状態適用例

#### SCR-001 ゲーム設定

- loading
  - 表示要素: [将来] 保存済みのデフォルト設定を取得中のインジケーター（v0 ではほぼ不要）。
  - 次アクション: 完了まで待つ。
- empty
  - 表示要素: 全入力欄は空またはデフォルト値; 「まずはプレイヤー数とゲームタイプを選択してください」。
  - 次アクション: 各フォーム入力 → 「ゲーム開始」押下。
- error
  - 表示要素: 入力バリデーションエラー（例: 「プレイヤー数は 2〜7 の範囲で入力してください」）をフォーム下に表示。
  - 次アクション: 入力値修正 → 再度「ゲーム開始」。
- success
  - 表示要素: 入力値が有効で CTA が活性化。
  - 次アクション: 「ゲーム開始」押下で GameScreen へ遷移。

#### SCR-002 ゲーム画面

- loading
  - 表示要素: 新ハンド開始時のカード配布中表示（短時間）；プレイヤー枠のスケルトンと「ハンドを準備中…」。
  - 次アクション: 進行開始を待つ。
- empty
  - 表示要素: まだゲームが開始されていない場合、「ゲーム設定から新規ゲームを開始してください」＋ `/` へのボタン。
  - 次アクション: ゲーム設定画面へ遷移。
- error
  - 表示要素: 「ゲーム状態に不整合が発生しました。ゲームをリセットしてください。」＋「ゲームをリセット」ボタン。
  - 次アクション: `reset` 実行 → SCR-001 へ戻る。
- success
  - 表示要素: 現在ストリート・アクター・プレイヤー情報・アクションボタンが正常に表示。
  - 次アクション: アクション入力、Next Hand で連続プレイ。

## 7. 共通UIコンポーネント一覧

### ナビゲーション

- `AppHeader`
  - 使用画面: 全画面
  - 必要なデータ: 現在ページ種別（設定 / ゲーム / 履歴）、ゲームタイプラベル（ゲーム中のみ）
  - バリエーション: 通常ヘッダ／「戻る」ボタン付きヘッダ（履歴詳細・ゲーム設定へ戻るなど）

- `BottomNav` [将来検討]
  - 使用画面: ゲーム画面＋履歴
  - 必要なデータ: 現在タブ（ゲーム / 履歴）
  - バリエーション: タブ 2 件構成（ゲーム中心のシンプルナビ）


### 詳細

- `HandSummaryPanel`
  - 使用画面: SCR-002（ショーダウン時）
  - 必要なデータ: gameType, playerCount, pot, winnerSeats, finishedAt
  - バリエーション: 通常表示／ショーダウン強調表示

- `StreetActionLog`
  - 使用画面: SCR-002
  - 必要なデータ: ストリート別 ActionLog（seat, action, amount）
  - バリエーション: ストリートごと折りたたみ／全展開モード

### フォーム

- `PlayerCountSelect`
  - 使用画面: SCR-001
  - 必要なデータ: 現在値, 選択可能範囲（2〜7）
  - バリエーション: セレクトボックス／ボタン群（2〜7 直接選択）

- `GameTypeSelect`
  - 使用画面: SCR-001
  - 必要なデータ: gameType 値（Stud Hi / Razz / Stud8）
  - バリエーション: ドロップダウン／カード風ボタン

- `InitialStackInput`
  - 使用画面: SCR-001
  - 必要なデータ: 初期スタック数値, バリデーションルール
  - バリエーション: 数値入力＋プリセットボタン（例: 10k / 20k）

### フィードバック（トースト / アラート）

- `Toast`
  - 使用画面: SCR-002（Next Hand 開始、エラー軽微時）
  - 必要なデータ: メッセージ, 種類（success / error / info）, 自動クローズ時間
  - バリエーション: 成功トースト／エラートースト

- `InlineFormError`
  - 使用画面: SCR-001
  - 必要なデータ: 対象フィールド名, エラーメッセージ
  - バリエーション: 単一エラー表示のみ（シンプル）

### ダイアログ / モーダル

- `ConfirmResetDialog`
  - 使用画面: SCR-002
  - 必要なデータ: ダイアログ文言, onConfirm, onCancel
  - バリエーション: 「ゲームをリセットしますか？」専用で OK/キャンセルのみ。

- `ErrorDialog` [将来]
  - 使用画面: 全画面
  - 必要なデータ: エラーメッセージ, 再試行ハンドラ
  - バリエーション: 重大エラー時のみ使用。

## 8. 情報設計と優先順位ルール

### ゲーム設定画面（SCR-001）

- 上部: ページタイトル＋簡単な説明（例: 「Stud Trainer: 練習用ゲームをセットアップ」）。
- 中央: 入力フォーム（プレイヤー数 → ゲームタイプ → 初期スタック）の順で縦並び。
- 下部固定: 主 CTA「ゲーム開始」ボタン。
- 優先順位ルール:
  - 必須入力（プレイヤー数・ゲームタイプ・スタック）をスクロールなしで全て見えるようにする。
  - 補助説明や将来の高度な設定（ブラインド構造など）は折りたたみセクションに [仮定]。

### ゲーム画面（SCR-002）

- 最上部: ゲームタイプ・現在のストリート・ポット合計（ゲーム全体のコンテキスト）。
- その直下: 現在アクター・Bring-in プレイヤーを視覚的に強調（色・アイコン・バッジ）。
- 中央: プレイヤー一覧（自分の行は常に画面内に見える位置に固定することを推奨）。
  - 各行: 名前 → スタック → ベット額 → カード表示 → 状態（fold / active）。
- 最下部固定: アクションボタン群（現アクターにのみ表示）＋補助ボタン（ログ折りたたみなど）。
- 優先順位ルール:
  - 「いま誰のアクションか」「何ができるか」が 1 秒以内に理解できることを最優先。
  - ログや細かい履歴は折りたたみ／別タブ扱いで、画面を圧迫しない。

## 9. 非機能 / UI 観点の制約

- **デバイス**
  - React + TypeScript + Vite + Tailwind の SPA として実装。
  - モバイルファーストで 1 カラムレイアウトを基本とし、PC では横幅を 600〜800px 程度の中央カラムに制限して読みやすさを確保。
  - タップターゲットは最小 44px 角を目安にする。

- **アクセシビリティ（必要最低限）**
  - コントラスト比を確保し、ゲームタイプ別の色分けに依存しない（ラベルやアイコンで補助）。
  - ボタンにはテキストラベルを必ず付ける（アイコンのみ禁止）。
  - キーボード操作でも主要操作（アクション選択・Next Hand）が行えるようフォーカス遷移を意識。

- **オフライン / ローカル前提**
  - v0 はバックエンド・DB なしで、全状態を Zustand（メモリ）で管理。
  - 通信エラーは基本発生しないため、通信前提のローディング UI は最小限。

- **パフォーマンス / 実装制約**
  - 個人開発であるため、コンポーネント設計は過剰に汎用化せず、「画面 2〜4 枚＋共通部品数個」で完結させる。
  - ゲームロジックは `utils/*` に分離し、UI は `useGameStore` を介して読み書きする構造を維持。

※このブリーフをベースに、まずは **SCR-001 / SCR-002 + FLOW-001〜003** を最小セットとして実装することを推奨します。
